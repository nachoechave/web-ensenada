# Aceptación de riesgo de producción — cpanel-dml, versión 1

El perfil preferido es **per-table**. Este perfil alternativo permite exactamente SELECT, INSERT, UPDATE y DELETE sobre la base literal `ensenada_web`, al usuario existente `ensenada_web_app@localhost` (127.0.0.1 permitido solo como cuenta local alternativa). No admite DDL, privilegios globales efectivos, otras bases, roles SQL heredados ni GRANT OPTION. El guion bajo debe aparecer escapado en el grant de base: `ensenada\_web`; un patrón sin escapar también podría coincidir con otras bases. USAGE sobre *.* no concede privilegios efectivos y se admite. La cuenta de esquema existente debe tener ALL PRIVILEGES únicamente sobre esa misma base literal, sin delegación; permanece fuera de procesos web. No se requieren ni se conceden nuevos privilegios.

## Riesgos que la aceptación debe mencionar

Una inyección SQL o robo de la credencial de ejecución permite alterar/borrar filas de **todas** las tablas: usuarios y roles, versiones de token, sesiones, mutexes, contenido, documentos y auditoría. Puede elevar roles de una cuenta propia, anular revocaciones, eliminar registros o falsificar eventos. El trigger conserva la revocación normal pero no protege contra un atacante con DML sobre sus tablas. Los FK/constraints no prueban que una operación fue autorizada. El usuario de esquema puede además modificar estructuras y triggers dentro de esta base. Sin GRANT OPTION no puede conceder privilegios, pero su ALL sigue siendo una credencial de alto impacto que debe custodiarse fuera de la aplicación web.

Laravel no convierte este usuario en una cuenta con auditoría append-only. Roles, CSRF, Origin, Fetch Metadata, validación de entradas, transacciones, consultas parametrizadas y sesiones seguras limitan ataques desde las rutas normales; no restringen el SQL ejecutado directamente con una credencial robada. Compartir UID Unix permite que una ejecución remota de código lea secretos o cambie archivos de ambos backends y sus controles locales. Las claves separadas no aíslan una cuenta Unix ya comprometida. La aceptación permite asumir estos riesgos residuales; no los elimina ni aprueba automáticamente el portal.

## Controles exigidos y límites

- Se mantienen la transferencia exclusiva, el aparcado de staging, la rotación de contraseña MySQL y cierre de conexiones propias, claves independientes, revocación autorizada, HTTPS, roles reales y el bloqueo de Bearer. El perfil alternativo no abre rutas ni modifica Apache.
- No existe endpoint que actualice o elimine auditoría. Noticia y auditoría se guardan en la misma transacción. Archivo y documento siguen siendo privados; las referencias y estados se validan en los controladores existentes.
- Se comprueban los grants exactos y los mutexes requeridos. La cuenta de esquema no se incorpora al .env del runtime. No se intenta ejecutar GRANT/REVOKE con cuentas que carecen de delegación. No se cambia el esquema.
- Antes de activar se requiere un respaldo completo restaurado en un contenedor aislado y la aprobación manual de contenidos, además de una aceptación identificada por responsable y referencia de autorización.
- Un checkpoint captura HMAC por ID de las filas observadas de auditoría, sin exponer su contenido. Debe conservarse con SHA y copia externa bajo otra custodia. Verificarlo detecta filas observadas eliminadas, modificadas o insertadas retroactivamente y cierra la API ante un fallo. No repara ni sobrescribe datos.
- Programar y comprobar verificaciones periódicas, y generar nuevos checkpoints después de verificar el anterior. Guardar también nuevas copias externas y respaldos completos. Entre observaciones un atacante puede insertar y borrar eventos sin dejar un checkpoint: ese intervalo y cualquier auditoría anterior al primer checkpoint constituyen riesgo residual. Un checkpoint no identifica por sí solo si un nuevo evento es legítimo.
- El HMAC y estado locales protegen frente a una modificación solo de SQL, no frente a compromiso del UID/clave de control. La copia externa y su hash custodiado fuera del hosting son necesarios para detectar sustitución o pérdida local; esta herramienta no puede certificar que una persona realmente hizo esa copia. La declaración explícita debe aportar su referencia de evidencia. No llamar a esta solución WORM, inmutable ni equivalente al perfil por tabla.
- Definir responsables de respuesta, frecuencia de verificación y objetivo de pérdida máxima entre backups. Ante alerta: detener publicación, conservar evidencia, rotar credenciales con autorización, comparar contra la copia externa y restaurar solo en entorno aislado antes de decidir una recuperación. No aceptar un nuevo checkpoint para ocultar cambios anteriores.

El responsable autorizado debe aceptar cada riesgo del formulario privado y aportar las referencias de custodia externa, monitoreo e incidentes. La activación y la recuperación requieren además `--accept-cpanel-dml-production-risk`; una variable .env o un permiso DML por sí solos no autorizan producción. El perfil estricto sigue siendo el predeterminado. La aceptación no tiene una ventana automática de 30 minutos ni reemplaza la revisión periódica documentada; se vincula a esta versión exacta de la política. Un cambio en la política exige nueva aprobación antes del corte.

Referencia primaria: [MariaDB GRANT](https://mariadb.com/docs/server/reference/sql-statements/account-management-sql-statements/grant). MariaDB interpreta comodines en grants de base y exige GRANT OPTION para conceder privilegios; no se intentan eludir esas restricciones.
